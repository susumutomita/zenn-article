クラウド競技を作るとき、最初にAWSサービスを選ぶと失敗しやすくなります。

「Lambdaを使った問題を作りたい」「VPCを触らせたい」という出発点では、参加者が何を学んだのかを判定できません。先に決めるべきなのは、競技終了後に参加者が**どの行動を自力でできるようになるか**です。

## 「AWSを理解する」では採点できない

次の目標は広すぎます。

> AWSの障害対応を理解する。

理解したかどうかを観察できないためです。代わりに、行動として書きます。

> HTTP 5xxを観測したとき、CloudWatch Logsとサービス状態を確認し、原因となるプロセス停止を特定して復旧できる。

この形なら、競技環境、成功条件、ヒント、振り返りを設計できます。

よい学習目標は、次の3点を含みます。

1. **状況**: 何が起きたときか
2. **行動**: 参加者が何をするか
3. **判定**: 何をもって成功とするか

Cloud Rescueの目標をこの形で書くと、次のようになります。

| 項目 | 内容 |
| --- | --- |
| 状況 | WebページまたはAPIのヘルスチェックが失敗している |
| 行動 | `SSM Session Manager`で対象ホストへ入り、systemdの状態とログを確認する |
| 判定 | nginxとAPIが再起動し、2つのエンドポイントがHTTP 200を返し続ける |

## 一つの問題に一つの主役を置く

初心者向け問題で、VPC、IAM、EC2、nginx、CloudWatch、SSMを同時に壊すと、何を学んでいるのか分からなくなります。

周辺サービスは使っても構いませんが、**今回判断してほしい対象を一つに絞ります**。

Cloud Rescueの最初の版では、主役を「Linuxサービスの状態確認と復旧」にします。

- VPCは最初から通信可能
- IAMはSSM接続に必要な範囲を構築済み
- EC2は起動済み
- 修正対象はnginxまたはAPIサービスの停止だけ
- 正常化はHTTP 200で自動判定

これなら、参加者が迷っても原因空間が広がりすぎません。

## 誤解を先に書き出す

問題作者は正解を知っているため、参加者がどこで迷うかを過小評価します。実装前に、想定する誤解を列挙します。

Cloud Rescueでは、次の誤解が考えられます。

- EC2への接続にはSSH鍵が必須だと誤認する
- プロセスが落ちているのにSecurity Groupを変更し続ける
- `systemctl start`だけを実行し、ログを確認しない
- frontendだけ直してAPIの復旧を忘れる
- 一度HTTP 200が返れば競技終了だと誤認する
- 新しいEC2を作り直そうとする

誤解は、ヒントと評価基準の材料になります。ただし、全てを問題文で先回りして説明すると探索する楽しさが消えます。最初の問題文は状況とゴールだけを示し、具体的な観察場所はヒントへ分けます。

## 評価基準を作る

得点だけでなく、何を観察したいかを決めます。

### 必須の評価

- 参加者が自分のAWS環境へ接続できた
- 対象サービスの状態を確認できた
- サービスを復旧できた
- frontendとAPIの両方が正常になった
- 正常状態を一定時間維持できた

### 振り返りで確認する評価

- 最初に何を疑ったか
- どの証拠で仮説を変えたか
- 復旧だけでなく再発防止をどう考えたか
- 監視がなければ障害にどう気づくか

機械採点に向かない項目は、無理に自動化しません。競技中はHTTP状態を採点し、思考過程は振り返りで扱います。

## 難易度を操作する4つのつまみ

同じ構成でも、次の要素で難易度が変わります。

### 1. 観測可能性

- 易しい: 対象インスタンスと接続コマンドをOutputに出す
- 普通: 対象は分かるが、停止サービスは伏せる
- 難しい: 複数インスタンスや複数ログから原因を絞る

### 2. 原因の数

- 易しい: nginxが停止している
- 普通: nginxとAPIのどちらか一方が停止している
- 難しい: 時間経過で別の障害が追加される

### 3. 成功条件

- 易しい: 一度HTTP 200になればflagを得る
- 普通: 2つのエンドポイントが継続して正常
- 難しい: フェーズごとに正常条件が変わる

### 4. 時間圧

- Challenge: 時間制限を弱くし、学習を優先する
- Battle: 1分ごとの加点・減点で復旧速度を競う

本書では、最初にChallengeとして理解させ、その後Battleへ発展させます。

## 競技設計シート

実装前に次のMarkdownを埋めます。

```markdown
# Cloud Rescue 競技設計

## 対象者
AWSの基本操作を経験したことがある初学者

## 学習目標
HTTP障害を観測し、SSMで接続し、systemdとログから停止サービスを特定して復旧できる

## 開始状態
EC2、nginx、Python APIは構築済み。いずれかのサービスが停止している

## 参加者が見る症状
frontendまたはAPIのヘルスチェックが失敗している

## 勝利条件
frontend `/` とAPI `/healthz` がHTTP 200を返す

## 禁止する解法
新しいトップレベルリソースを手作業で作ること

## 想定時間
Challenge 30〜45分、Battle 60〜90分

## 想定する誤解
Security Groupだけを変更し続ける、SSH鍵が必要だと思う、一方だけ直して終える

## ヒント
1. 接続経路
2. systemdの確認方法
3. 復旧コマンド

## 削除条件
CloudFormation stack削除後にEC2、EIP、ログ、SSM関連リソースが残らない
```

ここまで書ければ、必要なAWSリソースと採点方式が自然に決まります。
