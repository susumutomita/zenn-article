競技の設計は、Dockerfileや脆弱なコードから始めません。参加者が競技を終えたときに、何を理解し、何をできるようになってほしいかを先に決めます。

参加者は、時間を使って競技へ参加します。問題作者が見せたい技術ではなく、参加者が持ち帰れる経験を中心に置くと、不要な仕掛けや採点を減らせます。

本章では、最初に作るローカルChallengeの`sqli-demo`だけを設計します。AWS ChallengeとBattleは、まだ考えません。

## 学びを行動で書く

「SQL Injectionを理解する」だけでは、問題の内容と成功判定が決まりません。次の3点で書きます。

1. どの状況で
2. 何を行い
3. 何を確認できるようになるか

`sqli-demo`で参加者に持ち帰ってほしいことは、次のように書けます。

> ログイン画面の入力がSQL文へ安全でない形で組み込まれている状況で、入力による挙動の違いを調べ、認証を回避した後に、パラメータ化クエリが必要な理由を説明できる。

この文章から、問題に必要なものが決まります。

| 必要なもの | 本書で用意する内容 |
| --- | --- |
| 調査対象 | スタッフ専用のログイン画面 |
| 参加者の操作 | ユーザー名とパスワードへ入力し、挙動を比べる |
| 成功の証拠 | 管理者としてログインしたときだけ表示されるflag |
| 採点 | Participant Portalへ提出したflagを`/verify`で判定する |
| 解答後の学び | 安全でないSQLの組み立て方と修正方法を説明する |

## 中心となる行動を一つにする

この問題の中心は、ログイン画面の入力を変えながら挙動を観測することです。

データベースサーバーの構築、AWSへのデプロイ、複数の脆弱性探索は入れません。問題に関係しない準備が増えると、参加者がどこで止まったのか分からなくなります。

最初のローカルChallengeで体験してほしい流れは、次のとおりです。

1. Participant Portalで問題を開く
2. Web画面を開く
3. 入力によるログイン結果の違いを調べる
4. 管理者としてログインし、flagを発見する
5. flagをParticipant Portalへ提出する
6. 採点結果と解説を確認する

## 参加者が考える場所を残す

すべての操作を問題文へ書くと、参加者は手順をなぞるだけになります。一方、入口まで隠すと調査を始められません。

`sqli-demo`では、次を最初から示します。

- 調査対象がスタッフ専用ログイン画面である
- 管理者としてログインすると合言葉を取得できる
- 攻略対象のWeb画面を開くURL

次は示しません。

- 脆弱性の名前
- 認証を回避する入力
- 実行中のflag

参加者は、目的と入口を理解したうえで、入力処理を自分で調べます。

## 実装前の設計メモ

ここまでの判断を、1ページの設計メモへまとめます。

```text
問題名:
  スタッフ専用ログイン

参加者に持ち帰ってほしいこと:
  入力による挙動を調べ、認証回避の原因と修正方法を説明できる

最初の一手:
  Participant Portalからログイン画面を開く

中心となる操作:
  ユーザー名とパスワードの入力を変え、結果を観測する

成功の判定方法:
  管理者画面で得たflagを/verifyが正解と判定する

行き詰まったときの戻し方:
  入力処理への着目から、具体的なSQL Injectionの入力へ段階的に導く

終了方法:
  make local-downでローカル環境を停止する
```

この時点では、`metadata.json`やDockerfileの項目を決めていません。先に参加者の体験を確定し、次章でストーリー、勝利条件、安全境界へ変換します。
