難しい問題がよい問題とは限りません。参加者が何も分からないまま時間切れになると、測れるのは事前知識の差だけです。

ヒントは難易度を下げるためだけの機能ではありません。探索の範囲を少しずつ狭め、最後まで自分の手で操作させるための設計です。

## ヒントを3段階に分ける

Cloud Rescueでは、次の順番でヒントを出します。

### 第1段階: 観察場所を示す

> EC2へはSSHではなくSSM Session Managerで接続できます。Stack Outputの接続コマンドを確認してください。

まだ原因やコマンドは教えません。「入口が分からない」という競技外の詰まりを解消します。

### 第2段階: 調査方法を示す

> 接続後、`systemctl --failed`と`systemctl status nginx`でサービス状態を確認してください。状態が`failed`または`inactive`なら、`journalctl -u nginx`で直近のログを確認します。

観察対象を絞りますが、復旧操作は参加者に委ねます。

### 第3段階: 復旧操作を示す

> nginxが停止している場合は、設定を確認したうえで`sudo systemctl restart nginx`を実行し、`curl`で再確認します。

最終ヒントでは完走を優先します。それでも参加者自身が接続し、コマンドを実行し、結果を確認します。

## ペナルティの目的

ヒントのペナルティは罰ではありません。自力で進むか、学習を優先して先へ進むかを参加者が選ぶための仕組みです。

初学者向けChallengeでは、ペナルティを軽くするか、ゼロにしても構いません。Battleではヒントを公開するタイミングを運営判断にし、全チームへ同時に案内する方法もあります。

次の基準が使えます。

| ヒント | 内容 | 例のペナルティ |
| --- | --- | --- |
| 1 | 接続先や観察場所 | 小 |
| 2 | コマンドやサービス名 | 中 |
| 3 | 復旧手順に近い情報 | 大 |

得点の大小より、参加者がどこで詰まったかを記録できることの方が重要です。

## 問題文、ヒント、解説を分離する

3つの役割を混ぜないようにします。

### 問題文

- 状況
- ゴール
- 制約
- 利用できる入口

### ヒント

- 観察範囲を段階的に狭める
- 詰まりやすい環境操作を補助する
- 最後まで操作を参加者に行わせる

### 解説

- 原因
- 調査の順序
- 正規解法
- 別解
- 実運用での再発防止
- なぜこの問題を作ったか

問題文へ解説を書き込むと、探索がなくなります。解説をヒントへ隠すと、解けた人が学びを整理できません。

## README.ja.mdの構成

問題ディレクトリの日本語READMEを、次の構成にします。

```markdown
# Cloud Rescue — 停止したWebを復旧せよ

## ストーリー
公開直前のfrontendが停止した。担当SREとして復旧する。

## 学習目標
- SSM Session ManagerでEC2へ接続する
- systemdとjournalから障害原因を調査する
- 外形監視で復旧を確認する

## 構成
- EC2 1台
- nginx: port 80
- Python API: port 8080
- SSM Session Manager

## 参加者に見える症状
- frontendは失敗
- APIは正常

## 解法
1. Stack OutputからSSM接続コマンドを取得する
2. 対象EC2へ接続する
3. systemctlでnginxの停止を確認する
4. journalctlで意図しない設定エラーがないことを確認する
5. nginxを再起動する
6. curlとParticipant Portalで復旧を確認する

## なぜ起きたか
競技開始時にnginxだけが停止するように構成されている。

## 実運用なら
- systemdの自動再起動
- 外形監視
- アラートとrunbook
- デプロイ後のsmoke test
を検討する。

## 削除
CloudFormation stack削除後に残存リソースがないことを確認する。
```

英語版`README.md`も同じ情報構造にします。片方だけ更新して内容がずれないようにします。

## 問題文に書きすぎない

次のような問題文は、操作手順をなぞるハンズオンになります。

> Outputのコマンドをコピーし、SSMで接続し、`systemctl restart nginx`を実行してください。

Cloud Rescueでは、最初は次の程度にします。

> 顧客向けWebページが停止しています。APIは応答しています。既存環境を調査し、frontendをHTTP 200へ復旧してください。

接続方法が分からない人にはヒント1、Linux調査で止まる人にはヒント2を出します。

## 初見者の行動を記録する

レビューでは、正解したかだけでなく次を記録します。

- 最初にどこを見たか
- 何分でAWS環境へ接続できたか
- どのヒントを使ったか
- 誤った仮説は何だったか
- 復旧後に何を確認したか
- 問題文で誤解した表現は何か

作者が想定していない詰まりは、次版の改善材料です。操作環境で詰まった人を「AWSの知識がない」と片付けず、学習目標と関係のない摩擦は導線で減らします。

次章では、schema検証だけでなく、実AWS上でデプロイ、解答、削除まで通して確認します。
