[TenkaCloud](https://github.com/susumutomita/TenkaCloud)という、問題環境の準備から採点までを扱う競技プラットフォームを作っています。マルチクラウドの競技問題を共通形式で作るための仕組みも備えていますが、実際のクラウド実行はAWSを中心に扱っています。これまでは、実際のAWSアカウントでクラウドの問題を解く使い方を中心に紹介してきました。

今回、手元のPCで大会を開催できるように、大きく作り直しました。目玉は暗号バトルです。主催者のPCで起動し、同じネットワークにいる仲間がブラウザから参加できます。AWSアカウントも、クラウドへのデプロイも要りません。この構成で暗号バトルを開催するためのクラウド利用料はかかりません。

念頭にあったのは、東大のブロックチェイン公開講座のような、暗号やブロックチェインを学ぶ場です。講義で聞いた暗号を、隣の人と競いながら触れたら面白い。研究室や対面の勉強会で使うなら、参加者全員にAWSアカウントを用意してもらうより、主催者のPCを開いて始められるほうが合っています。

## 暗号を解くことと、情報を公開することが競技になる

暗号バトルは、問題を順番に解いて終わりではありません。チームごとに秘密の情報を持ち、届いたお題を解きながら得点を競います。

お題には締切があります。自分で計算して答えるか、**LEAK**を選んで、指定された情報を公開する代わりに得点するか。公開された情報は、相手が秘密を見破る**HUNT**の材料になります。目先の得点を取るために出した情報が、後で相手の得点につながるわけです。

たとえばシーザー暗号で「2を暗号化すると5になる」と公開されたら、差から鍵の3を求められます。HUNTでは、公開された暗号文を写すのではなく、そこから復元した秘密を提出します。RSAのお題では、公開された数を作った素数を求めます。

解き方と競技のルールは、[暗号バトルの参加者向け説明](https://github.com/susumutomita/TenkaCloudChallenge/blob/4bb3a116c545fc46ed6a39ffcc5117fb914947f4/battles/ac26-crypto-battle/README.ja.md)にまとまっています。画面で得点や残り回数を確認しながら進められるので、まずは少人数で一度遊んでみてください。

![2チームの暗号バトルで計算模型のお題を解き、30点を得てランキング1位になる画面](/images/tenkacloud-local-crypto/tenkacloud-classroom-crypto.gif)

2チームの暗号バトルをlocalhostで動かした収録です。計算模型のお題を解いて30点を獲得し、ランキングに反映されるところまでを示しています。待ち時間は編集し、非公開の値を隠しています。別端末からLAN経由で参加する様子を収録したものではありません。

## 主催者のPCで起動し、チームキーを渡す

主催者側は、macOS、Linux、またはWSL2でGit、Make、Bun 1.3.11を用意します。暗号バトル自体にはDockerは不要です。Dockerを使う別の問題も選ぶ場合は、Docker EngineとCompose v2が必要になります。

起動するコマンドは以下です。

```bash
git clone --recurse-submodules https://github.com/susumutomita/TenkaCloud.git
cd TenkaCloud
make install
make local
```

ソースコードや依存パッケージを取得する初期セットアップには、インターネット接続が必要です。PCとネットワークを使うので、機材や電力まで含めて費用がゼロという意味でもありません。

起動すると、主催者画面と参加者ポータルのURLがターミナルに出ます。通常は、それぞれ`http://127.0.0.1:5174`と`http://127.0.0.1:5175`です。主催者は、対話的な起動時に一度表示される主催者キーでログインします。

大会を始める流れは次のとおりです。

1. 大会を作り、2チーム以上と**Cryptography Battle**を選ぶ。
2. **Deploy now**で競技を準備する。この問題ではAWSリソースを作らない。
3. チームごとの参加者URLとチームキーを渡す。
4. **Schedule**から**Start now**で大会を開始する。
5. 参加者が問題を開いて**Ready**を押す。全チームが準備できるとお題が始まる。

参加者はTenkaCloudをインストールしません。主催者から受け取ったURLをブラウザで開き、自分のチームキーで入ります。問題を解いて提出し、相手の公開情報を見てHUNTする。得点は参加者画面とランキングに反映されます。

### 別のPCから参加する

研究室や対面イベントでは、主催者のPCのプライベートIPv4アドレスを指定して起動します。

```bash
make local LOCAL_ARGS="--lan 192.168.1.20 --unsafe-lan"
```

`192.168.1.20`は例なので、実際のPCのアドレスに置き換えます。主催者画面は引き続きループバックで待ち受け、参加者ポータルを指定したLANに公開します。暗号バトルだけなら、参加者用のポート、デフォルトでは5175番をファイアウォールで許可します。

このLANモードはHTTPです。信頼できる隔離されたイベント用ネットワークで使い、インターネットへポート転送しないでください。`--unsafe-lan`は、その条件を明示して選ぶためのオプションです。詳細は[別のPCから参加する手順](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/docs/local-hosting.md#participants-on-another-computer)を参照してください。

### 止めても、得点と大会の状態を残す

別のターミナルから`make down`を実行すると、データを残して停止します。同じcheckoutとデータディレクトリで`make local`を実行すると、保存した大会を再開できます。

ただし、再起動で競技の時計がリセットされるわけではありません。暗号バトルを新しくやり直すなら、新しい大会を作ります。全員の採点を終える操作は**End Event**です。チーム単位のStopやTear downとは役割が違います。

主催者キーをなくした場合は、対話的に`make local-reset`を実行すると再発行できます。大会、得点、参加者キーを消さずに、古い主催者キーとセッションだけを失効させます。通常の対話的な`make local`での再起動でも、新しい主催者キーが表示されます。

## ローカル開催の単位を「1つの大会ホスト」にした

今回の設計で揃えたのは、問題を解く前に必要な準備です。主催者が大会を作り、問題を選び、チームキーを渡す。参加者は受け取ったポータルから入る。この流れを、ローカル開催でも通常の主催者画面と参加者画面で扱うようにしました。

ローカルのアプリケーションサーバーはBunの単一プロセスです。大会や得点はSQLiteに保存します。ローカル開催のためにCognitoや外部データベースを用意する必要はありません。

暗号バトルでは、そのプロセス内で実際の問題プラグインを動かします。対戦の状態は共有しますが、参加者に返すのは、そのチームの保管庫と公開情報だけです。試合全体の秘密や他チームの保管庫はホスト側に残します。状態、得点、操作の再試行に必要な記録もSQLiteへ保存します。

この実装は、[HTTPとSQLiteを使った暗号バトルのテスト](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/scripts/local-host/tests/coordination-http.test.ts)でも確認しています。ログインして得点するだけでなく、別大会との分離、再起動後の再開、採点ロックを検証する内容です。

一方、AWSサービスを操作する問題はクラウド開催に残しました。ローカル版にAWS向けの設定を持ち込まず、実行できる問題だけを選べるようにしています。暗号バトルのオプションにあるAWS Parameter Storeを使う課題も、ローカル開催では有効にしていません。

## 大改修で、既存の運用手順まで失いかけた

構成を整理する中で反省したのは、以前の`deploy`や`destroy`に入っていた運用上の知見を、作り直した経路で落としてしまったことです。画面から大会を作れるだけでは、これまで使っていた人が配置し、更新し、片付けるところまで引き継げません。

復旧では、環境ごとの設定、CDK bootstrap、ソースのアップロード、既存スタックの識別を確認しました。撤収も、所有するリソースと削除ポリシーを確認して処理する形に戻しました。[クラウドの配置・撤収手順](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/infrastructure/README.md#current-checkouts-setup-and-teardown-boundary)に現在の境界を記録しています。

たとえば、大会の問題環境をTear downする操作と、開催基盤を`make destroy`で消す操作は別です。通常のdestroyで外部Tursoのデータまで消えるとは限りません。保持されたストレージや問題リソースは課金対象になり得ます。ローカルの停止と削除についても、`make down`とデータを消す操作を分けました。

リファクタリングで守るべきなのは、APIやテーブルの形式だけではなかった。利用者がどの環境を選び、何を残し、どう撤収するかも、引き継ぐ対象でした。そこをコードと手順の両方で確認する必要がありました。

現在のREADMEでは、クラウド版は統合候補として扱っています。実AWSでの大会リハーサルと、ホストされた暗号バトルの性能確認は残っており、既存データの自動移行にも対応していません。[対応範囲と検証の境界](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/docs/host-retirement.md)を分けて案内しています。

## まず、同じ部屋で一度競ってみる

今回作りたかったのは、研究室や勉強会で「次はこれを一緒にやろう」と言える競技環境です。主催者のPCで起動し、仲間にURLとチームキーを渡す。暗号を解く楽しさと、公開した情報を相手に使われる感覚を、その場で体験できます。

離れた場所から参加させる用途には、TLSプロキシの後ろでセルフホストする構成もあります。ただ、これは補足の選択肢です。コンテナ構成は暗号バトルの検証用で、Docker問題を実行する構成とは別です。[セルフホストの条件](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/docs/local-hosting.md#hosting-behind-a-tls-proxy)を確認してください。

まずはローカルで2チームの大会を作って、Readyから得点まで試してみてください。TenkaCloudを説明するより、実際に1試合やってもらうほうが、今回の改修で変えたかったことが伝わります。
