[TenkaCloud](https://github.com/susumutomita/TenkaCloud)という、クラウドの問題をチームで解いて競うOSSを作っています。マルチクラウドの問題を共通形式で作れるようにしていますが、クラウド上での競技はAWSを中心に実装してきました。

機能を増やすうちに、ローカル、SaaS、Lite、ホストの4つのモードになってしまい、使い分けが難しくなりました。そこで、ホストモードをローカルモードへ統合しました。SaaSモードは、実際に試してくれたユーザーから利用したいという声が出なかったことと、保守性を考えて一旦廃止しました。

この整理とローカルモードの改修で、手元のPCでも競技を開催できるようになりました。暗号バトルなら、主催者のPCで起動して、同じネットワークにいる仲間がブラウザから参加できます。AWSアカウントとDockerは不要で、この開催にクラウド利用料はかかりません。

念頭にあったのは、東大のブロックチェイン公開講座のような、暗号やブロックチェインを学ぶ場です。研究室や対面の勉強会で、習った暗号を使って隣の人と競えたら面白い。この改修で、こうした場でもAWSアカウントを用意せずに遊べます。

## 計算して得点するか、情報を公開して得点するか

暗号バトルでは、チームごとに秘密の情報を持ち、届いたお題を解いて得点します。

お題には締切があります。自分で計算して答えるほかに、**LEAK**を選んで指定された情報を公開し、得点する方法もあります。公開された情報は、相手が**HUNT**で秘密を見破るために使えます。計算を省いて得点すると、そのぶん相手に手がかりを渡すことになります。

たとえばシーザー暗号で「2を暗号化すると5になる」と公開されたら、差から鍵の3を求められます。HUNTには、その復元した鍵を提出します。RSAのお題なら、公開された数を作った素数を求めます。得点や残り回数は画面で確認できます。詳しいルールは[参加者向け説明](https://github.com/susumutomita/TenkaCloudChallenge/blob/4bb3a116c545fc46ed6a39ffcc5117fb914947f4/battles/ac26-crypto-battle/README.ja.md)にまとめています。

![2チームの暗号バトルで計算模型のお題を解き、30点を得てランキング1位になる画面](/images/tenkacloud-local-crypto/tenkacloud-classroom-crypto.gif)

これはlocalhostで2チームの大会を動かした収録です。計算模型のお題を解いて30点を獲得し、ランキングに反映されています。待ち時間は編集し、非公開の値を隠しています。

## 主催者のPCで起動する

主催者側はmacOS、Linux、またはWSL2で、Git、Make、Bun 1.3.11を用意します。

```bash
git clone --recurse-submodules https://github.com/susumutomita/TenkaCloud.git
cd TenkaCloud
make install
make local
```

初期セットアップでは、ソースコードや依存パッケージをインターネットから取得します。Dockerを使う別の問題も選ぶ場合は、Docker EngineとCompose v2が必要です。

起動すると、主催者画面と参加者ポータルのURLがターミナルに出ます。通常はそれぞれ`http://127.0.0.1:5174`と`http://127.0.0.1:5175`です。主催者は、対話的な起動時に一度表示される主催者キーでログインします。

大会の準備は画面から行います。

1. 大会を作り、2チーム以上と**Cryptography Battle**を選ぶ。
2. **Deploy now**で競技を準備する。暗号バトルではAWSリソースを作らない。
3. チームごとの参加者URLとチームキーを渡す。
4. **Schedule**から**Start now**で大会を開始する。
5. 参加者が問題を開いて**Ready**を押す。全チームが準備できるとお題が始まる。

参加者はTenkaCloudをインストールせず、受け取ったURLをブラウザで開いてチームキーを入力します。お題を解いて提出し、相手が公開した情報からHUNTする操作まで、参加者ポータルで行えます。

### 同じネットワークの別PCから参加する

主催者のPCのプライベートIPv4アドレスを指定すると、参加者ポータルをLANに公開できます。

```bash
make local LOCAL_ARGS="--lan 192.168.1.20 --unsafe-lan"
```

`192.168.1.20`は例なので、実際のPCのアドレスに置き換えます。暗号バトルだけなら、ファイアウォールで参加者用の5175番ポートを許可します。主催者画面はループバックで待ち受けます。

このモードはHTTPなので、信頼できる隔離されたイベント用ネットワークで使い、インターネットへポート転送しないでください。設定の詳細は[LAN参加の手順](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/docs/local-hosting.md#participants-on-another-computer)にあります。今回の収録はlocalhostで行い、別端末からのLAN接続は未検証です。

### 停止と、やり直しを分けた

別のターミナルから`make down`を実行すると、データを残して停止します。同じcheckoutとデータディレクトリで`make local`を実行すると、得点や大会の状態を引き継ぎます。

再起動しても競技の時計はリセットしません。新しい試合を始めるなら大会を作り直します。全員の採点を終えるときは**End Event**を使います。

主催者キーをなくしたときは、対話的に`make local-reset`を実行すると再発行できます。古い主催者キーとセッションを失効させ、大会、得点、参加者キーは残します。対話的な`make local`での再起動でも、新しい主催者キーを表示します。

## BunとSQLiteで大会を動かす

ホストモードをローカルへ統合し、個人練習も大会とチームを使って進める構成にしました。LiteモードのAWS開催機能はCloudとして残し、ローカル開催とクラウド開催の2つに整理しました。ローカルでも主催者が大会を作り、参加者へチームキーを渡します。主催者画面と参加者ポータルは、既存の画面を使っています。

ローカルのサーバーはBunの単一プロセスで動き、大会や得点をSQLiteに保存します。Cognitoや外部データベースを用意する必要はありません。

暗号バトルの問題プラグインも、そのプロセス内で実行します。ホストは試合全体の状態を持ち、参加者には自チームの保管庫と公開情報を返します。他チームの保管庫や試合全体の秘密は返しません。試合の状態と操作の再試行に必要な記録をSQLiteへ保存するので、同じデータで再起動できます。

[HTTPとSQLiteを使うテスト](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/scripts/local-host/tests/coordination-http.test.ts)では、実際の問題プラグインでLEAKとHUNTを実行しています。得点とランキング、別大会との分離、再起動後の再開、採点ロックを確認します。

AWSサービスを操作する問題はクラウド開催で扱います。ローカルではAWSリソースを作らず、実行できる問題だけを選べるようにしました。暗号バトルにあるAWS Parameter Storeを使うオプションも、ローカルでは無効です。

## deployとdestroyの運用手順も復旧した

大改修の途中で、以前の`deploy`や`destroy`に入っていた運用上の知見を、新しい実装から落としてしまいました。ローカルで大会を作れても、クラウド版を配置して更新し、使い終わったリソースを片付ける手順が抜けていました。

復旧では、環境ごとの設定、CDK bootstrap、ソースのアップロード、既存スタックの識別を確認しました。撤収時には、リソースの所有者と削除ポリシーを確認してから処理します。[配置と撤収の手順](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/infrastructure/README.md#current-checkouts-setup-and-teardown-boundary)も書き直しました。

問題環境のTear downと、開催基盤の`make destroy`は別の操作です。外部Tursoのデータは通常のdestroyでは残ります。保持されたストレージや問題リソースは課金対象です。ローカルでも、データを残す`make down`とデータを消す操作を分けています。

今回抜けていたのは、画面やAPIの機能よりも、使っていた環境を次の版へ更新する手順でした。既存のコマンドで何を配置し、何を残し、何を消していたかまで確認してから作り直す必要がありました。

クラウド版は現在のREADMEでも統合候補として扱っています。実AWSでの大会リハーサルとホストされた暗号バトルの性能確認は残っており、既存データの自動移行にも対応していません。[対応範囲](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/docs/host-retirement.md)に記録しています。

## 研究室や勉強会で使うなら

まずは主催者のPCで2チームの大会を作り、Readyから得点まで試せます。参加者へ渡すのはURLとチームキーなので、対面の勉強会でも準備を説明しやすくなりました。

離れた場所から参加させる場合は、[TLSプロキシの後ろでセルフホストする構成](https://github.com/susumutomita/TenkaCloud/blob/56c3cb13189c8b06d994c938e3a83e752ca4b702/docs/local-hosting.md#hosting-behind-a-tls-proxy)もあります。このコンテナ構成は暗号バトルの検証用で、公開サーバーでの運用は未実施です。
